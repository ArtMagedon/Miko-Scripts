## Общие правила

- Скрипты предназначены для личной автоматизации и запуска из терминала.
- Пути с пробелами и кириллицей следует заключать в кавычки.
- Перед первым запуском скрипта, который перемещает или удаляет файлы, рекомендуется проверить его на тестовой папке.
- Скрипты не следует запускать через `sudo`, если это прямо не требуется: некоторые из них изменяют файлы в домашнем каталоге пользователя.
- Если команда не находится, проверь, что скрипт исполняемый и его каталог добавлен в `PATH`.

## Установка и запуск

Рекомендуемое расположение пользовательских скриптов:

```text
~/Scripts/Miko/
```

Создай каталог:

```bash
mkdir -p ~/Scripts/Miko
```

Скопируй в него нужные скрипты и выдай права на исполнение. Например:

```bash
chmod +x ~/Scripts/Miko/*
```

Чтобы запускать команды из любой директории, добавь каталог в `PATH`. Если каталог ещё не добавлен, выполни:

```bash
grep -qxF 'export PATH="$HOME/Scripts/Miko:$PATH"' ~/.bashrc || \
  printf '\nexport PATH="$HOME/Scripts/Miko:$PATH"\n' >> ~/.bashrc

source ~/.bashrc
```

После этого скрипты можно запускать по имени, например:

```bash
git-tools help
```

Название команды зависит от имени самого исполняемого файла. Если файл называется `organize-files`, запускай его как `organize-files`, а не как `organize_files.sh`.

## 1. Git Tools — работа с Git

**Файл:** `git-tools`

**Назначение:** единая Bash-команда для типовых операций с Git: создания локального репозитория, настройки пользователя, подготовки SSH для GitHub, получения и отправки изменений, а также проверки состояния репозитория.

`git-tools` — один компонент более крупного набора скриптов Miko. Он не заменяет Git и не пытается автоматически разрешать конфликты или объединять разошедшиеся ветки.

### Установка Git Tools

Помести исполняемый файл `git-tools` в каталог скриптов, например `~/Scripts/Miko/`, затем выполни:

```bash
chmod +x ~/Scripts/Miko/git-tools
```

Если каталог добавлен в `PATH`, проверь работу команды:

```bash
git-tools help
```

### Команды Git Tools

| Команда        | Назначение                                                                                                  |
| --------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `git-tools help`    | Показать справку                                                                                       |
| `git-tools version` | Показать версию                                                                                         |
| `git-tools create`  | Создать локальный репозиторий и добавить удалённый адрес `origin` |
| `git-tools config`  | Настроить глобальные `user.name` и `user.email`                                               |
| `git-tools ssh`     | Настроить SSH-ключ для подключения к GitHub                                               |
| `git-tools pull`    | Получить изменения из удалённой ветки                                                |
| `git-tools push`    | При необходимости создать коммит и отправить изменения                |
| `git-tools sync`    | Определить, нужно ли отправить или получить коммиты                       |
| `git-tools status`  | Показать состояние репозитория и удалённые адреса                         |

Для команд `pull`, `push`, `sync` и `status` можно указать путь к репозиторию. Если путь не задан, используется текущая директория.

### Аргументы и примеры Git Tools

#### `create` — создать репозиторий

Интерактивный запуск:

```bash
git-tools create
```

С передачей пути и URL:

```bash
git-tools create Projects/site git@github.com:user/site.git
```

Путь без начального `/` считается относительным к домашнему каталогу. Например, `Projects/site` означает `$HOME/Projects/site`.

Если передать только путь, скрипт запросит URL:

```bash
git-tools create Projects/site
```

Управление первоначальной загрузкой удалённой ветки:

```bash
git-tools create Projects/site git@github.com:user/site.git --no-pull
git-tools create Projects/site git@github.com:user/site.git --pull
```

- `--no-pull` — пропустить первоначальную загрузку.
- `--pull` — автоматически выполнить `git pull --ff-only origin main`.
- Без этих параметров скрипт спросит, нужно ли загружать удалённую ветку.

Команда создаёт только новый путь, который ещё не существует. Если удалённый репозиторий не содержит ветку `main` или имеет несовместимую историю, первоначальная загрузка может завершиться ошибкой.

#### `config` — настроить имя и email

Интерактивный запуск:

```bash
git-tools config
```

Передать оба значения:

```bash
git-tools config "Artem Example" artem@example.com
```

Передать только имя:

```bash
git-tools config "Artem Example"
```

Передать только email:

```bash
git-tools config "" artem@example.com
```

Если значение не передано, скрипт запросит его интерактивно. Команда изменяет **глобальные** настройки Git текущего пользователя, то есть они применяются по умолчанию ко всем его репозиториям, если в конкретном репозитории не заданы локальные значения.

#### `ssh` — настроить SSH для GitHub

Интерактивный запуск:

```bash
git-tools ssh
```

Задать комментарий нового ключа, обычно email:

```bash
git-tools ssh --comment artem@example.com
```

Создать ключ без passphrase для неинтерактивного сценария:

```bash
git-tools ssh --comment artem@example.com --no-passphrase
```

Параметр `--no-passphrase` создаёт закрытый ключ без парольной защиты. Это менее безопасно при компрометации учётной записи, поэтому использовать его следует только при осознанной необходимости.

Passphrase намеренно не принимается обычным аргументом командной строки: аргументы могут сохраняться в истории оболочки или быть видимыми другим процессам.

Скрипт использует ключ `~/.ssh/personal_key`. Если ключ уже существует, он не перезаписывается. Скрипт добавляет запись `Host github.com` в `~/.ssh/config`, только если такая запись не найдена. Уже существующая запись автоматически не исправляется — проверь, что она использует нужный `IdentityFile`.

В конце скрипт показывает публичный ключ. Его нужно добавить в настройках GitHub: **Settings → SSH and GPG keys**.

#### `pull` — получить изменения

```bash
git-tools pull
git-tools pull "$HOME/Projects/site"
```

Перед загрузкой скрипт проверяет наличие незакоммиченных изменений. Если они есть, операция прекращается. Используется `git pull --ff-only`, чтобы не создавать неожиданный merge-коммит.

#### `push` — отправить изменения

```bash
git-tools push
git-tools push "$HOME/Projects/site"
```

Если найдены локальные изменения, скрипт показывает статус и спрашивает подтверждение перед добавлением файлов в индекс и созданием коммита. Затем отправляет текущую ветку на `origin`.

#### `sync` — синхронизировать репозиторий

```bash
git-tools sync
git-tools sync "$HOME/Projects/site"
```

Скрипт получает сведения об удалённой ветке и сравнивает её с локальной:

- если ветки совпадают, сообщает, что синхронизация не требуется;
- если локальная ветка впереди, отправляет локальные коммиты;
- если удалённая ветка впереди, получает изменения через fast-forward;
- если обе ветки содержат независимые коммиты, прекращает работу и предлагает разрешить расхождение вручную.

Если есть незакоммиченные изменения, скрипт предлагает создать коммит перед синхронизацией.

Если путь не указан, используется текущая директория. Для `pull` применяется
`--ff-only`; `sync` не объединяет автоматически разошедшиеся ветки.

`push` и `sync` автоматически создают коммит, если есть незакоммиченные
изменения. Текст коммита генерируется по типам изменений — вводить его вручную
не требуется. По умолчанию используется короткий заголовок со счётчиками:

```text
Update (+2 ~1 -1 >0)
```

Здесь `+` — добавленные файлы, `~` — изменённые, `-` — удалённые, `>` —
переименованные. Чтобы включить в коммит перечень всех файлов, добавь `--full`:

```bash
git-tools push full                  # текущий репозиторий
git-tools push ~/Projects/site --full  # указанный репозиторий
git-tools sync full
git-tools sync ~/Projects/site --full
```

В режиме `--full` заголовок остаётся коротким, а в теле коммита выводятся
отдельные сгруппированные списки добавленных, изменённых, удалённых и
переименованных файлов. Так все изменения перечислены, но заголовок не
превращается в длинную строку. Пути к файлам сохраняются целиком; у переименований
указываются старое и новое имя. Режим включает изменения, которые Git видит после
`git add -A`, в том числе удаления.

#### `status` — посмотреть состояние

```bash
git-tools status
git-tools status "$HOME/Projects/site"
```

Показывает путь к репозиторию, текущую ветку, настроенные удалённые адреса и краткое состояние рабочей директории.

### Ограничения Git Tools

- Скрипт не разрешает конфликты слияния автоматически.
- `pull` использует fast-forward и не выполняет автоматический merge.
- `sync` прекращает работу, если локальная и удалённая ветки разошлись.
- `ssh` показывает публичный ключ, но не добавляет его в аккаунт GitHub автоматически.
- Перед использованием `push` и `sync` на важных проектах проверь `git status` и убедись, что изменения можно коммитить.

## 2. File Organizer — раскладывание файлов по папкам

**Файл:** `organize-files` (рекомендуемое имя; фактическое имя файла может отличаться)

**Назначение:** переместить каждый обычный файл из указанной директории в отдельную подпапку, названную по имени файла без последнего расширения.

### Использование

```bash
organize-files "/путь/к/папке"
```

Например:

```bash
organize-files "$HOME/Downloads"
```

Скрипт требует ровно один аргумент — путь к существующей директории. Если аргумент не передан или директория не существует, скрипт завершится с сообщением об ошибке.

### Пример

До выполнения:

```text
Downloads/
├── photo.jpg
├── video.mp4
├── archive.tar.gz
├── README
└── .config.json
```

После выполнения:

```text
Downloads/
├── photo/
│   └── photo.jpg
├── video/
│   └── video.mp4
├── archive.tar/
│   └── archive.tar.gz
├── README/
│   └── README
└── .config/
    └── .config.json
```

Скрипт убирает **только последнее расширение**. Поэтому `archive.tar.gz` перемещается в `archive.tar/`, а не в `archive/`. Для имени без точки расширение не удаляется. Для скрытых файлов, начинающихся с точки, поведение Bash-шаблона может выглядеть непривычно: например, `.config.json` превращается в каталог `.config`.

### Что обрабатывается

- Обычные файлы верхнего уровня указанной директории, включая скрытые.
- Пробелы и кириллица в именах поддерживаются.
- Существующие вложенные директории не обходятся рекурсивно.
- Символические ссылки и директории не обрабатываются как обычные файлы.

### Важные ограничения

Скрипт **перемещает файлы**, а не копирует их. Если директория с рассчитанным именем уже существует, команда `mkdir` завершится ошибкой; из-за `set -e` скрипт остановится. Поэтому сначала рекомендуется проверить результат на тестовом каталоге или сделать резервную копию важных файлов.

## 3. Yaru 24 Places Theme Builder — создание тем значков

**Файл:** `yaru-24-places` (рекомендуемое имя; фактическое имя файла может отличаться)

**Назначение:** собрать пользовательские темы значков на основе каталогов `places` из Yaru 24, чтобы использовать прежний вид значков папок в более новой среде Ubuntu/Yaru. Дополнительно копируются указанные файлы файлового менеджера, а для совместимости создаётся символическая ссылка `file-manager.png` на `filemanager-app.png`.

Скрипт не устанавливает тему из системного пакета: он формирует локальные каталоги тем и ссылки в домашнем каталоге пользователя.

### Источники и расположение результата

В текущей версии заданы следующие пути:

```bash
SOURCE="$HOME/yaru-24/usr/share/icons"
REPO="$HOME/.themes/yaru-24-places"
ICON_DIR="$HOME/.local/share/icons"
```

- `SOURCE` — каталог с исходными темами Yaru 24.
- `REPO` — место, где формируются пользовательские темы.
- `ICON_DIR` — место, где создаются символические ссылки на эти темы.

Перед запуском каталог `SOURCE` должен существовать и содержать ожидаемые исходные темы.

### Какие темы создаются

Скрипт обрабатывает список, указанный в массиве `THEMES`:

- `Yaru`
- `Yaru-bark`
- `Yaru-blue`
- `Yaru-dark`
- `Yaru-magenta`
- `Yaru-olive`
- `Yaru-prussiangreen`
- `Yaru-purple`
- `Yaru-red`
- `Yaru-sage`
- `Yaru-viridian`

Имена результатов получают префикс `Yaru-24`. Например, из `Yaru` создаётся `Yaru-24`, а из `Yaru-magenta` — `Yaru-24-magenta`.

### Дополнительные файлы

Массив `COPY_PATHS` определяет дополнительные файлы, которые нужно копировать из каждой исходной темы:

```bash
COPY_PATHS=(
    "*/apps/filemanager-app.png"
    "*/apps/file-manager.png"
)
```

Список можно изменять в самом скрипте. Шаблоны трактуются как пути относительно каталога конкретной исходной темы.

Если найден `filemanager-app.png`, скрипт также создаёт рядом символическую ссылку `file-manager.png`, указывающую на `filemanager-app.png`.

### Как устроена работа

Для каждой темы скрипт:

1. Проверяет наличие исходного каталога.
2. Удаляет предыдущий каталог результата с таким же именем и создаёт его заново.
3. Находит все каталоги `places` и копирует их с сохранением структуры.
4. Копирует дополнительные файлы, указанные в `COPY_PATHS`.
5. Создаёт `index.theme` с именем темы, наследуемой темой и перечнем скопированных каталогов.
6. Создаёт символическую ссылку в `~/.local/share/icons`.
7. В конце выводит список созданных тем и ссылок.

### Запуск

```bash
yaru-24-places
```

Параметры командной строки текущей версией не предусмотрены: настройки задаются в начале файла.

После выполнения темы будут сформированы в `~/.themes/yaru-24-places`, а ссылки — в `~/.local/share/icons`. Чтобы выбрать тему, используй настройки внешнего вида или соответствующие средства GNOME.

### Важные ограничения

- Скрипт использует жёстко заданные пути и список тем.
- Если отсутствует хотя бы один каталог темы из массива `THEMES`, скрипт завершится с ошибкой.
- Перед пересозданием каталога результата скрипт выполняет `rm -rf` для конкретного пути `"$REPO/$NEW_THEME"`. Не изменяй `REPO` без проверки значения: ошибка в пути может привести к удалению не тех файлов.
- Скрипт формирует `index.theme` из найденных каталогов `places` и дополнительных файлов. Корректность результата зависит от структуры исходной темы и правил текущего окружения GNOME/Yaru.
- Сам скрипт не переключает текущую тему значков автоматически.

## file_excavator — перемещение и переименование файлов

Скрипт обрабатывает файлы в указанном каталоге и его подкаталогах первого уровня. Файлы из подкаталогов перемещаются в основной каталог, при этом имя исходного подкаталога добавляется к имени каждого файла через символ `_`.

**Порядок работы:**

1. Запрашивает путь к каталогу.
2. Запрашивает подстроку для замены и новую подстроку.
3. Заменяет заданную подстроку в именах файлов основного каталога.
4. Перемещает файлы из подкаталогов в основной каталог, добавляя к их именам название исходного подкаталога и символ `_`.
5. Удаляет опустевшие подкаталоги.
6. Выводит исходный и конечный пути каждого переименованного или перемещённого файла.

Если поле `replace` оставить пустым, замена подстроки не выполняется, но файлы из подкаталогов всё равно перемещаются в основной каталог с добавлением названия исходного подкаталога.

**Пример работы:**

```
dir:   /home/user/Documents
replace: old
to:    new

/home/user/Documents/old_file.txt => /home/user/Documents/new_file.txt
/home/user/Documents/folder/file.txt => /home/user/Documents/folder_file.txt
```

**Запуск:**

```
chmod +x file_excavator
./file_excavator
```

Скрипт обрабатывает только файлы основного каталога и файлы непосредственно внутри его подкаталогов. Более глубокие уровни вложенности рекурсивно не обходятся. Если файл с целевым именем уже существует, скрипт пропускает перемещение, чтобы не перезаписать существующий файл.

## Безопасность и ограничения

Перед запуском любой новой утилиты просмотри её содержимое. Для проверки синтаксиса Bash можно использовать:

```bash
bash -n ~/Scripts/Miko/имя-скрипта
```

Эта проверка обнаруживает синтаксические ошибки, но не доказывает корректность логики и не гарантирует безопасное поведение при любых входных данных.

Особенно внимательно проверяй скрипты, которые:

- перемещают или удаляют файлы;
- изменяют пользовательские настройки;
- используют `sudo`;
